# Общая память агентов

agentmemory — отдельный приватный сервис для допущенных проектных VM. Все
допущенные клиенты используют одну память: названия проектов упорядочивают
записи, но не изолируют доступ. Для изолированного проекта поднимайте собственную
память и не включайте эту интеграцию.

## Устройство сервиса

Конфигурация развёртывания: `memory-vm`, VMID **103**, IP **10.210.0.107**;
2 vCPU, 8 ГиБ RAM, системный диск 20 ГиБ и отдельный диск данных 100 ГиБ,
монтируемый по UUID в `/srv/agentmemory`. Ballooning: минимум 6 ГиБ, максимум 8 ГиБ. Сервис работает от непривилегированного
пользователя под systemd; без диска данных запуск запрещён. Включены автозапуск
VM и защита от удаления. Один физический хост не обеспечивает HA. Шаблоны
развёртывания: [systemd unit](../ops/agentmemory/agentmemory.service),
[окружение сервера](../ops/agentmemory/server.env.example) и
[настройка кеша модели](../ops/agentmemory/cache.mjs). При развёртывании генерируйте
секреты отдельно; значения примеров нельзя использовать как готовые ключи.

Закреплённые версии: [agentmemory 0.9.30](https://www.npmjs.com/package/@agentmemory/agentmemory/v/0.9.30)
и [iii-engine 0.22.1](https://github.com/iii-hq/iii/releases/tag/v0.22.1).
Включены локальные embeddings; при первом использовании может потребоваться
скачивание модели. Внешняя LLM-компрессия и извлечение графа по умолчанию выключены.
Данные, индексы и кеш модели сохраняются на диске данных. Внешние бэкапы пока
не настроены: RAID не восстанавливает ошибочно удалённые или повреждённые данные.

| Адрес | Назначение | Доступ |
| --- | --- | --- |
| `https://10.210.0.107` | API общей памяти | Только IP явно допущенных VM |
| `127.0.0.1:3111` | Внутренний API | Только loopback сервисной VM |
| `127.0.0.1:3112` | Внутренние streams | Только loopback сервисной VM |
| `127.0.0.1:3113` | Viewer | Только SSH-туннель |
| `127.0.0.1:49134` | Внутренний worker | Только loopback сервисной VM |

Caddy проверяет индивидуальный ключ и IP клиента, затем подставляет внутренний
секрет backend. Проектные VM внутренний секрет не получают. Proxmox Firewall
дополнительно ограничивает доступ к сервисной VM. Публичных пробросов портов,
изменений WireGuard и публичных сервисов на pxmx нет.

## Выдать доступ новой VM

Обновите клиент vmctl и worker до **0.9.1**, затем проверьте конфигурацию:

```sh
vmctl config validate
vmctl create project-vm debian small --with-system agentmemory --dry-run
vmctl create project-vm debian small --with codex,claude,opencode --with-system agentmemory
vmctl info project-vm
```

Для обменника одновременно используйте `--with-system fileshare,agentmemory`.
В TUI включите **agentmemory** в группе **System features**. По умолчанию она
выключена; пока worker не настроен, флажок недоступен и рядом указана причина.
Первая версия поддерживает гостей Debian/Ubuntu; неподдерживаемые семейства
получают понятную ошибку.

Возможность устанавливает клиентские компоненты, а не сервер в каждой VM и не
самих ИИ-агентов. После завершения bootstrap настраиваются обнаруженные
поддерживаемые Codex, Claude Code и OpenCode. Совместимый Node используется
повторно либо устанавливается для интеграции; development-модуль Node сам по
себе не выбирается. Другие MCP-серверы и настройки агентов сохраняются. Ключ
лежит в отдельном пользовательском файле `0600`, частный CA закреплён. Секреты
не попадают в сводки CLI/TUI и метаданные Proxmox.

Поддержка MCP и автоматического сохранения различается между адаптерами.
Дождитесь cloud-init и проверьте реальные инструменты MCP внутри агента.
Результат создания показывает **запрошенные** адаптеры, а не подтверждённую
настройку гостя. При недоступности сервиса возникает явная ошибка; отдельная
локальная память незаметно не создаётся. Поддерживаемые hooks используют
ограниченную очередь повторной отправки.

## Hooks Codex требуют отдельной проверки доверия

MCP в Codex работает и без включённых native hooks. Установка или включение
плагина **не** означает разрешение его hooks: Codex требует проверки текущих
определений. При первом интерактивном запуске Codex выполните `/hooks` и
проверьте только те определения agentmemory, которым намерены доверять.
Не используйте `--dangerously-bypass-hook-trust`; vmctl не меняет глобальное
доверие к hooks. См. [документацию OpenAI](https://developers.openai.com/plugins/build/plugins).
Шаг настройки клиента выводит напоминание об этой проверке.

Если native-плагин agentmemory уже включён, vmctl не устанавливает второй набор
hooks. Когда существующее окружение native-плагина нельзя безопасно изменить,
настройка сообщает, что его remote endpoint нужно проверить. Убедитесь, что
этот плагин использует общий endpoint и свой защищённый файл ключа; успешная
настройка MCP сама по себе этого не подтверждает. Текущая локальная agentmemory
рабочего компьютера и её записи остаются без изменений.

Успешный MCP-вызов или прямой тест hook не подтверждает доверие и работу
автосохранения native Codex. Это проверяется отдельно в настоящей сессии агента
после разрешения hooks. Проверка развёртывания не выполняет вход в аккаунт агента
и платный запрос и без такой сессии не объявляет native-автосохранение проверенным.

## Проверить работу

В подготовленной VM проверьте cloud-init и подключение установленных агентов:

```sh
cloud-init status --wait
codex mcp list
claude mcp list
opencode api mcp.list
```

Выполняйте только команды для установленных агентов. В OpenCode **2.0.31** команда
`opencode mcp list` может ошибочно показывать `No MCP servers`, даже для сервера,
добавленного штатной командой. Проверяйте реальное подключение через
`opencode api mcp.list`; см. [документацию OpenCode v2](https://dev.opencode.ai/v2/docs/mcp-servers/).
Проверено, что событие `session.create` native-плагина OpenCode попадает в общую
память как `session-start` без запроса к LLM и входа в аккаунт (ноль токенов).
Это подтверждает данный путь сохранения; native hooks Codex всё ещё требуют
описанного выше разрешения доверия.

Внутри агента посмотрите
доступные инструменты памяти, сохраните безобидную запись с уникальным текстом,
найдите её, затем найдите со второго допущенного клиента. Это проверяет общий
backend, а не просто наличие имени MCP-сервера. Автосохранение проверяйте
отдельно: завершите короткую сессию поддерживаемого агента и найдите её запись.
Не вставляйте клиентский ключ в команды терминала или сообщения.

Viewer открывается через доверенный SSH jump на Proxmox. На рабочем компьютере
в отдельном терминале:

```sh
ssh -N -J pxmx -o ExitOnForwardFailure=yes -L 127.0.0.2:3113:127.0.0.1:3113 -L 127.0.0.2:3112:127.0.0.1:3112 vmadmin@10.210.0.107
```

Откройте `http://127.0.0.2:3113`. Нужны оба проброса: agentmemory 0.9.30 выбирает
порт live-канала 3112 из ответа health, поэтому отдельный проброс страницы на
другой порт не перенаправляет live-канал. Другой loopback-адрес не мешает
существующим сервисам на `127.0.0.1`. Сервер разрешает origin
`http://127.0.0.2:3113`; локальный proxy viewer подставляет авторизацию backend.
Не открывайте эти туннели на `0.0.0.0`.

Запускайте SSH в той же ОС, где работает браузер. Доступ к WSL-адресу
`127.0.0.2` из браузера Windows не проверялся; для браузера Windows можно
использовать нативный Windows OpenSSH и открыть туннели непосредственно в Windows.
Проверены HTTP-страница, live-метаданные, snapshot/search и WebSocket-транспорт;
визуальная работа интерфейса в браузере не проверялась.

## Конфигурация worker и жизненный цикл

Опциональный пример `[agentmemory]` есть в [`config.toml`](../config/config.toml).
На pxmx относительные пути отсчитываются от `/etc/vmctl`. Ключ управления —
обычный файл root с правами `0600`; `agentmemory-known-hosts` закрепляет
проверенный SSH host key сервисной VM. `agentmemory-ca.crt` — проверенный
публичный сертификат CA. Управление выполняется ограниченным SSH account/helper,
а не публичным административным API. Helper атомарно меняет реестр клиентов
и конфигурацию gateway, проверяет её перед reload и откатывает неудачное изменение.

Dry-run не создаёт ключи, разрешения или записи памяти. Проверка сервиса идёт
до клонирования. При неудачном создании компенсируются только ресурсы этой
операции. Перед удалением VM её индивидуальный доступ отзывается; ошибка
отзыва останавливает удаление. Записи памяти сохраняются. Клонирование VM с
действующими ключами памяти запрещено, чтобы копия не унаследовала доступ.
Сам сервер общей памяти — защищённая инфраструктурная VM.

CLI agentmemory может продолжить работать после падения дочернего iii.
Health-check timer systemd проверяет авторизованный локальный API с ограниченным
временем ожидания каждые 30 секунд, начиная через 90 секунд после загрузки,
и перезапускает сервис при неисправности API. Публичного health endpoint не
создаётся. Таймер дополняет перезапуск процесса; активный CLI сам по себе не
подтверждает восстановление. Восстановление после reboot проверяется отдельно.
Исходники: [проверка API](../ops/agentmemory/healthcheck.py),
[oneshot service](../ops/agentmemory/vmctl-agentmemory-healthcheck.service) и
[timer](../ops/agentmemory/vmctl-agentmemory-healthcheck.timer).

Для администрирования используйте доверенный SSH-доступ, статусы systemd и
журналы. Не выводите файлы окружения и секретов. Проверяйте монтирование диска
данных и восстановление после перезапуска. Сам по себе запущенный процесс
не подтверждает сохранность данных, ограничения клиентов или поиск записей.

## Локальные записи и перенос

CLI не переносит память рабочих станций автоматически. По отдельному разрешению
17 октября 2026 история локальной 0.9.28 перенесена на этот сервер. Подключения
локальных агентов не переключались, исходник не удалялся. Закрытые снимки исходных
данных и конфигурации, а также исходное состояние сервера сохранены на рабочей
станции и диске данных сервера.

Полный экспорт старой версии разрывал соединение worker. Поэтому использован
нативный снимок с краткой остановкой записи, проверкой каждого раздела через
iii 0.22.1 в изоляции, сравнением записей и проверкой поиска до подключения
рабочего сервиса. На исходнике iii 0.11.2: это проверенный перенос конкретных
версий, а не гарантия совместимости любых директорий БД. Новые записи за время
проверки объединены через штатный импорт. В проверенном снимке **137 сессий,
15 872 наблюдения, 1 845 memories и 27 lessons**; трём свежим memories добавлены
служебные сведения о происхождении из импорта. Производные индексы обновлены, связи
графа сохранены. Автокомпакция графа при старте отключена; обслуживание графа
остаётся отдельной операцией. Новая версия переносит audit в разделы по месяцам
и удаляет старый шум `index_persist`; полный исходный audit сохранён в снимке.

Ответ графа размером 136 МиБ выявил внутренний предел SDK в 100 МиБ. После
установки закреплённого серверного пакета запустите
[`tune_sdk.py`](../ops/agentmemory/tune_sdk.py) от root на `memory-vm`.
Скрипт задаёт ограниченный предел **256 МиБ** для iii-sdk **0.22.1**, проверяет
точную реализацию соединения и отказывается менять неизвестную версию или код.
Повторный запуск безопасен; после переустановки зависимости настройку повторяют.
Меняется только внутреннее loopback-соединение SDK, не внешний лимит загрузки
HTTP. Обновление upstream SDK требует проверки. Таймер восстановления проверяет
`/agentmemory/livez`: предупреждения CPU/задержки в `/health` не должны вызывать
перезапуски при нормальной индексации и поиске.

Для следующего переноса сначала проверьте штатный
[export/import](https://github.com/rohitg00/agentmemory) на копии: все типы записей,
ID, связи, пути, вложения и полноту индексов. Перед объединением сохраняйте обе
истории. Не заменяйте работающую БД и не считайте успешный импорт доказательством
полноты поиска.

## Подключение рабочих станций

Codex и Claude Code этой машины теперь настроены на приватный HTTPS endpoint.
Старый локальный сервер остановлен; его база и резервные копии конфигурации
сохранены. Дополнительная синхронизация при подключении не выполнялась. Настройки
OpenCode подготовлены, но его исполняемого файла на этой машине нет.

Каждому компьютеру нужны маршрут через WireGuard, собственный отзывной ключ,
разрешённый исходящий IP и проверенный CA. Шлюз принимает отдельную админскую
идентичность `workstation-<имя>-<32-hex-id>` с owner `workstation:<32-hex-id>`.
Проверяются одновременно ключ и точный исходящий IP, как для VM. Регистрация и
отзыв выполняются через существующий ограниченный SSH helper, а не публичный
админский API. Не используйте идентичность VM или внутренний секрет сервера.
При смене адреса WireGuard администратор должен явно обновить доступ. Отдельной
команды автоматической регистрации компьютеров в этой версии нет.

Локальный профиль находится в `~/.local/share/vmctl/agentmemory/`:
`access.json` и `ca.pem` доступны только владельцу; `run` читает ключ и запускает
закреплённый официальный remote bridge или capture hook. В конфигурациях агентов
хранятся только путь launcher и аргументы. Сертификат проверяется; отдельный
SSH-туннель не нужен. Ошибка подключения не запускает локальную fallback-память.
Резервные копии настроек:
`~/.local/state/vmctl/connections/20261017-remote-memory/before/`.

Перезапустите открытые сессии Codex/Claude, чтобы перечитать MCP и hooks.
В Codex через `/hooks` проверьте только новые определения agentmemory. Прежние
настройки доверия сохранены; разрешение native capture не выдаётся автоматически.
Hooks Codex добавлены в `config.toml` рядом с прежними, без второго файла
`hooks.json` на пользовательском уровне. У Claude дублирующий capture native-плагина
agentmemory выключен в пользу одного управляемого набора global hooks. Другие
плагины и MCP-серверы сохранены. Сохранённая настройка OpenCode обновлена без
утверждения, что отсутствующий executable был протестирован.

Проверить подключение без изменения памяти:

```sh
codex mcp get agentmemory
claude mcp get agentmemory
```

Живая проверка подтвердила 54 инструмента, запись/поиск только на сервере,
доставку capture, отказ без ключа и с неправильным ключом, работу при остановленной
локальном API. Платные запросы агентам и подтверждение доверия hooks Codex
не выполнялись.
