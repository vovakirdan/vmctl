# Общий файлообменник

SFTPGo — опциональный обменник между рабочим компьютером и выбранными VM.
Каждый проект продолжает жить на собственном диске своей VM. Для передачи
не нужны графическая среда, постоянное монтирование или отдельный демон в VM проекта.

## Сервис и доступ

Развёртывание использует Debian 13 `files-vm` (VMID 102, `10.210.0.105`): 2 vCPU,
2 ГиБ RAM, системный диск 20 ГиБ и отдельный диск данных 200 ГиБ в `/srv/files`.
SFTPGo Community запускается нативно через systemd от непривилегированного
пользователя. Зафиксирована версия [v2.7.6](https://github.com/drakkan/sftpgo/releases/tag/v2.7.6).

| Адрес | Назначение | Доступ |
| --- | --- | --- |
| `10.210.0.105:2022` | Обмен файлами по SFTP | WireGuard и явно допущенные VM |
| `https://10.210.0.105:8443/web/admin` | Администрирование | Только WireGuard и pxmx |

Сервис остаётся в приватной сети `vmbr1`. Публичное перенаправление портов и
изменение WireGuard не требуются. Firewall сервисной VM ограничивает сетевой
доступ; индивидуальные SSH-ключи, ограничения исходных IP и права SFTPGo
управляют доступом к файлам.

Допущенные VM читают общий каталог, но записывают только в собственную директорию
с уникальным именем. Учётная запись рабочего компьютера управляет всем обменником.
Для исключений используйте WebAdmin: например, запретите отдельный каталог или
дайте дополнительное право записи. Источник действующих прав — SFTPGo;
vmctl не ведёт отдельную БД и не сбрасывает права при обновлении.

Резервное копирование пока не настроено. RAID не защищает от удаления или порчи
данных. До подключения внешнего хранилища у файлов обменника нет независимой
копии для восстановления.

## Подключение с рабочего компьютера

Подключитесь через WireGuard под пользователем `workstation` со своим SSH-ключом:

```sh
sftp -P 2022 workstation@10.210.0.105
```

До подтверждения ключа сервера проверьте его отпечаток через доверенное SSH-подключение.
Публичный ключ сервера также записан в `fileshare.host_public_key` на pxmx.
Для нестандартного ключа добавьте `-i /path/to/private_key` к команде на компьютере;
приватный ключ не нужно копировать на files-vm. На Windows можно использовать
WinSCP с тем же адресом, SFTP-портом и SSH-ключом. Команды внутри OpenSSH SFTP:

```text
ls
put /local/path/archive.tar
get archive.tar /local/destination/archive.tar
put -R /local/path/folder
```

Для WebAdmin доверяйте частному центру сертификации только после получения его
сертификата через существующее доверенное SSH-подключение. Администраторские
данные хранятся на pxmx в `/etc/vmctl/fileshare-admin.json`, доступном только root.
Это не учётная запись гостевой VM. Не вставляйте их в отчёты, аргументы команд и чат.

## Доступ для новой VM

Сначала обновите клиент и worker до 0.8.0 и выполните `vmctl config validate`.
На worker уже должна быть рабочая конфигурация `[fileshare]`.

```sh
vmctl create project-vm debian small --with-system fileshare --dry-run
vmctl create project-vm debian small --with-system fileshare
vmctl info project-vm
```

В TUI та же опция находится в группе **System features**. Она отделена от Rust,
Node, Python и других модулей разработки. Существующие VM автоматически доступа
не получают. Dry-run не создаёт учётную запись и ключ.

При создании генерируются уникальные учётная запись и SSH-ключ, устанавливается
rclone и записывается отдельная конфигурация в `~/.config/vmctl/fileshare/`.
Ключ и конфигурация доступны только настроенному cloud-init пользователю.
Обёртка `vmctl-files` всегда использует эту конфигурацию, сохраняя
ваши существующие подключения rclone. Проверка SSH использует закреплённый
публичный ключ сервера.

Перед использованием дождитесь завершения cloud-init. Доступный SSH-порт и
успех `vmctl create` сами по себе не подтверждают завершение установки пакетов.

Внутри VM замените `YOUR_DIRECTORY` на уникальный каталог для записи из
`vmctl info`. Обёртка принадлежит root и установлена в
`/usr/local/bin/vmctl-files`, поэтому работает и в неинтерактивных SSH-командах.

```sh
vmctl-files lsf files:
vmctl-files copy ./archive.tar files:YOUR_DIRECTORY/ --progress
vmctl-files copy ./folder files:YOUR_DIRECTORY/folder --progress
vmctl-files copy files:YOUR_DIRECTORY/folder ./downloaded-folder --progress
vmctl-files deletefile files:YOUR_DIRECTORY/archive.tar --interactive
vmctl-files purge files:YOUR_DIRECTORY/folder --interactive
```

`copy` может заменить существующие файлы в вашем каталоге. Посторонние файлы
в каталоге назначения она не удаляет. `purge` удаляет выбранный каталог вместе
с содержимым; при ручном удалении оставляйте `--interactive`. Прогресс показывает
rclone; подробности — в [документации SFTP](https://rclone.org/sftp/).

Удаление VM отзывает её учётную запись, разрывает активные файловые подключения
и удаляет разрешение firewall. Загруженные файлы сохраняются для доступа с
компьютера. Если безопасно отозвать доступ не удалось, удаление VM прекращается.
Клонирование VM с активным доступом запрещено: на диске находится действующий
приватный ключ.

## Конфигурация worker и обслуживание

Добавьте опциональную секцию в `/etc/vmctl/config.toml` на pxmx. Пример намеренно
неполный: нужно указать настоящий публичный ключ сервера и доверенный сертификат.
Файл API-ключа содержит только API-ключ, а не JSON с администраторскими данными.

```toml
[fileshare]
endpoint = "https://10.210.0.105:8443"
sftp_host = "10.210.0.105"
sftp_port = 2022
host_public_key = "ssh-ed25519 REPLACE_WITH_VERIFIED_PUBLIC_HOST_KEY"
ca_file = "fileshare-ca.crt"
api_key_file = "fileshare-api-key"
shared_directory = "/srv/files/shared"
firewall_vmid = 102
firewall_ipset = "vmctl-files-clients"
timeout_seconds = 15
```

Относительные пути сертификата и ключа отсчитываются от каталога конфигурации
worker. Файл API-ключа должен принадлежать root и иметь права `0600`. Он нужен
только worker; его нельзя коммитить. Не отключайте проверку сертификата.
`config init` сохраняет существующие настройки, поэтому после обновления
интеграция настраивается явно. Отсутствие или ошибки настройки дают понятную
ошибку при подготовке доступа.

Закрепите один и тот же Ed25519-ключ с обеих сторон. В JSON-конфигурации нативного
SFTPGo задайте эти поля внутри `sftpd` и сохраняйте ключ при обновлениях:

```json
{
  "host_keys": ["/etc/sftpgo/id_ed25519"],
  "host_key_algorithms": ["ssh-ed25519"]
}
```

Иначе штатный пакет rclone из Debian 13 может выбрать ECDSA-ключ сервера,
тогда как known_hosts закрепляет Ed25519, и сообщить о несовпадении ключа.
Единственный проверенный Ed25519-ключ на сервере сохраняет строгую проверку
со штатным пакетом; не отключайте её ради обхода этой ошибки.

В этом развёртывании одновременно используются masquerading и firewall VM
Proxmox. Ограниченное правило conntrack назначает зону 1 трафику с `fwbr102i0`,
как описано в [документации Proxmox по masquerading](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#sysadmin_network_masquerading).
На хосте unit `vmctl-files-nat@102.service` восстанавливает это правило до
запуска `pve-guests.service`; шаблон находится в
[`ops/files-vm/vmctl-files-nat@.service`](../ops/files-vm/vmctl-files-nat@.service).
При переносе сервиса на другой VMID проверяйте firewall bridge и экземпляр
unit вместе. Это настройка развёртывания: обычное создание VM с `fileshare`
меняет только список разрешённых IP в firewall настроенной сервисной VM,
не устанавливая общие правила NAT или raw-таблицы хоста.

Диск данных должен монтироваться по UUID до запуска SFTPGo. Если `/srv/files`
не смонтирован, systemd должен запретить запуск сервиса. Кроме самих файлов,
сохраняйте БД SFTPGo и SSH host keys. При обслуживании сохраняйте владельцев
каталогов, а перед согласованной копией остановите сервис. Не удаляйте оставшиеся
каталоги VM при обычной очистке учётных записей.

Для проверки используйте `vmctl config validate`, `vmctl info files-vm`, статус
systemd и журнал SFTPGo. Не публикуйте полные конфигурации, cloud-init или ответы
API: там могут быть секреты. Сначала проверьте права на свежей одноразовой VM
и небольших файлах. Файлам около 50 ГБ нужно место одновременно под существующие
и поступающие данные; проверка маленьким файлом не подтверждает передачу 50 ГБ.
